# Служебные команды роутера

Роутер публикует [инструменты данных RSVData](tools-rsvdata.md) и 7
собственных: `register_target`, `unregister_target`, `list_targets`,
`update_targets`, `job_status`, `get_rsvdata`, `help_router`.

## Поведение при отсутствии бинарника RSVData

Роутер запускается и без `--rsvdatabinary` — недоступны только возможности,
которым нужен сам файл:

| Вызов | Без бинарника |
|---|---|
| `get_rsvdata` | отвечает инструкцией: путь не задан, перезапустите роутер с `--rsvdatabinary` |
| `GET /bin/rsvdata.cfe` | 404 с инструкцией |
| `update_targets` | отказ сразу: «Бинарник RSVData роутеру не выдан: запустите роутер с --rsvdatabinary …» |
| `register_target` с `install=true` | отказ на предпроверке ещё ДО пинга, фоновое задание не создаётся |
| `unregister_target` с `uninstall=true` | работает — в цепочке удаления бинарник не используется |
| `list_targets`, `job_status`, `help_router` | без разницы |

## Первые шаги

1. Зарегистрировать базу — одним из четырёх способов:

   **Если запущена EDT (доступен MCP:RSV) — регистрируйте с указанием cwd**
   (вариант «а», или cwd рядом с url/connection): cwd привязывает цель к
   проекту EDT, и `install=true` сможет установить расширение через EDT —
   без публикации и без данных авторизации. Без cwd регистрируйте, только
   когда воркспейса нет.

   ```
   # а) cwd воркспейса EDT — самый удобный вариант в агентском режиме:
   #    агент сам подставляет cwd своего текущего каталога, специально
   #    указывать параметры не нужно; из cwd роутер выводит проект EDT →
   #    ассоциированную ИБ → строку подключения → URL; cwd может быть
   #    корнем воркспейса или любым его подкаталогом — проект основной
   #    конфигурации (единственный с серверной базой) роутер определит
   #    сам; цель получает EDT-связь, и вызовы без base из этого
   #    воркспейса идут на неё
   register_target(cwd="D:\\dev\\edt-workspace\\UT")

   # б) адресом публикации базы — роутер хранит корень http://host/base и сам
   #    достраивает пути сервиса (/hs/rsvdata/mcp, /hs/rsvdata/update);
   #    полный адрес с /hs/rsvdata/mcp тоже принимается — хранится корень
   register_target(url="http://srv-1c/ut_demo",
                   base="ut_demo", comment="УТ 11.5")

   # в) строкой подключения — URL серверной базы строится сам (порт кластера
   #    отбрасывается), алиас берётся из Ref
   register_target(connection='Srvr="srv-1c:1541";Ref="acc30demo";')

   # г) названием базы из списка баз (1cestart, ibases.v8i) — имя должно
   #    совпадать ТОЧНО; url берётся из строки подключения записи, алиасом
   #    становится Ref
   register_target(base="Зарплата и управление персоналом (демо)")
   ```

   cwd вместе с url/connection тоже работает: цель привязывается к проекту
   EDT, если проект из cwd указывает на эту же базу (сравнение корня url).

   Строка подключения сохраняется в записи (`connection`, нормализованная
   `Srvr`/`Ref` без учётных данных) — из неё конфигуратор берёт параметры
   подключения при установке/удалении расширения. Надёжные источники —
   `connection`, `cwd` и название базы (порт кластера сохраняется).
   Регистрация ТОЛЬКО по url (вариант «б») оставляет запись без строки
   подключения: установить расширение на такую базу роутер не сможет —
   база пригодна для работы, установку выполнит администратор, удаление
   ограничено точкой `/remove`.

   Ответ содержит проверку связи (ping) и инструкцию по аутентификации.
   Файловые базы не поддерживаются (нет веб-публикации) — для них COM-мост.

2. Если база требует логин/пароль — ключ задаётся локально (никогда не через
   чат). Цель регистрируется сразу с шаблоном
   `"auth": { "type": "basic", "value": "" }`.

   **Основной способ — keyring ОС**, командой пакета (спросит логин и пароль,
   перезапуск роутера не нужен):
   ```bat
   rsv-data-router set-secret ut_demo          :: задать/заменить ключ
   rsv-data-router remove-secret ut_demo       :: убрать ключ
   ```
   Ключ хранится в keyring ОС (Windows Credential Manager / Secret Service в
   Linux) — в `targets.json` его нет, поэтому файл можно показывать и
   бэкапить. `unregister_target` keyring-запись не трогает — при удалении
   цели снимите ключ командой `remove-secret`.

   **Запасной вариант без keyring** (headless-сервер, CI) — секция `auth`
   в `targets.json`:
   ```json
   "auth": { "type": "basic", "value": "байтовая строка" }
   ```
   `value` — base64 от «логин:пароль» или готовая строка `Basic ...`:
   ```powershell
   [Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes("логин:пароль"))
   ```
   Инлайн-значение приоритетнее keyring-записи; пустое `value` — читать
   keyring. Перезапуск роутера не нужен: и keyring, и файл читаются при
   каждом вызове. База без авторизации: удалите секцию `auth` (комментариев
   в JSON нет) и не задавайте keyring-запись — запросы пойдут без
   Authorization.

3. Проверить: `list_targets` — `check=true` пингует каждую цель и для
   RSVData 1.3.5+ показывает версию и хеш расширения; `check=false` — без
   сетевых запросов.

4. Работать: `config` — паспорт базы; `query`/`execute_query` — данные;
   `get_structure`/`describe` — структура метаданных; `eventlog` — журнал
   регистрации; `reveal` — расшифровка анонимизации. База выбирается
   параметром `base`; без него — база из EDT по `cwd` (у цели есть EDT-связь),
   а если цель одна — она сама. `help` без параметров — справка
   роутера и список целей; `help topic=<имя>` — подробная справка RSVData.

## register_target

По умолчанию проверяет связь ping-ом (`check=False` — пропустить).
Повторная регистрация существующей цели
(`register_target(base="алиас")`) использует сохранённые имя, url и EDT-связь
записи — `url` из вызова игнорируется (защита от опечатки или устаревшего
адреса); `connection` из вызова адрес не меняет — только пополняет/обновляет
сохранённую строку подключения; удобно для переустановки расширения.

Способы регистрации, формат строки подключения и настройка ключа —
в «Первых шагах» выше; состав записи — «Формат targets.json» в
[development.md](development.md).

### Установка расширения (`install=true`)

Ключ `install=true` (работает только вместе с `check=true`) ставит/обновляет
расширение RSVData (бинарник `--rsvdatabinary`) на регистрируемой базе:
точка `/update` → при ошибке EDT через MCP:RSV (нужна EDT-связь цели —
регистрируйте с cwd) → конфигуратор (точная сборка платформы базы; соседние
сборки не взаимозаменяемы — нет нужной, вариант конфигуратора отклоняется).
Публикация базы для установки НЕ нужна — она требуется только для проверки:
EDT и конфигуратор работают с базой напрямую.

Конфигуратору, кроме версии, нужен источник строки подключения: EDT-связь
цели или сохранённая в записи `connection` (из строки подключения, cwd или
названия базы при регистрации); из url строки НЕ выводится — на одном
веб-сервере может быть несколько кластеров, поэтому цель только с url
установку не выполнит (см. «Первые шаги»).

Ключ авторизации для конфигуратора НЕ обязателен: без него конфигуратор
запускается без `/N /P` (базы без пользователей; в отчёте будет пометка),
заданный, но нечитаемый ключ — отказ «данные авторизации повреждены,
установите заново» (`rsv-data-router set-secret`). Неудачный запуск
конфигуратора приводит хвост журнала `/Out` в отчёт задания КАК ЕСТЬ —
другого текста ошибки конфигуратор не отдаёт.

Версия платформы базы для конфигуратора определяется автоматически, по
убыванию приоритета: EDT-связь цели (`.infobase-binding`, затем `Version`
её записи) → оффлайн-скан всех воркспейсов, которые помнит стартер EDT
(`%LOCALAPPDATA%\1C\1cedtstart\projects.json` — работает и при закрытой
EDT; проект ищется по совпадению host+ref строки подключения) → `Version`
записи `ibases.v8i`, совпавшей по Srvr/Ref (точная сборка из параметров
самой базы; `DefaultVersion` сознательно не используется). Если источники
молчат, а на машине установлена ровно ОДНА платформа — конфигуратор-вариант
использует её (в отчёте будет пометка); при нескольких установленных —
запросите версию у пользователя и перерегистрируйте цель с ключом
`platform` (номер версии, например `8.3.27.2214`, ИЛИ полный путь к
`1cv8.exe`): ключ хранится в записи, хранится и подхватывается
`uninstall=true`; авто-резолв всегда приоритетнее ключа.

Перед запуском установки — предпроверка: если заранее известно, что ни один
вариант не сработает (роутеру не выдан бинарник `--rsvdatabinary`; нет
источника строки подключения — регистрация по url; или не определена версия
платформы), ошибка с диагностикой и следующим шагом возвращается сразу,
фоновое задание не создаётся.

Установка идёт ФОНОВЫМ ЗАДАНИЕМ: вариант конфигуратора занимает минуты и
синхронный ответ умирает по таймауту клиента. Ответ `register_target` несёт
id задания; статус и построчный отчёт — `job_status(job_id="ид")`, опрашивайте
раз в 20–30 с. Повторный `install=true` по цели с идущим заданием отклоняется.

В конце цепочки — проверка доступности: она назовёт, чего не хватает, и
следующий шаг для каждого пункта — «публикация не обнаружена → выполнить
публикацию», «данных авторизации нет → добавить ключ (rsv-data-router
set-secret)», оба сообщения сразу, когда не хватает и того и другого. Отсюда
цепочка укладывается в один вызов, если базе не нужна авторизация, и в два
иначе: после добавления ключа — повторная проверка (ping или
`list_targets check=true`), установка при повторе не требуется. Неудавшаяся
установка подсказывает повтор: `register_target(install=true, check=true)`
или `update_targets`. Каждый шаг завершается понятной строкой («Расширение
обновлено через /update», «Расширение установлено через конфигуратор»,
«Публикация не обнаружена…» и т.п.); `check=false` ключ `install` игнорирует.
Логика установки — `installer.py`, вариант конфигуратора переиспользует
`update_designer.py` (креды из targets.json, в лог не попадают; отсутствие
ключа — запуск без авторизации, читайте выше).

## unregister_target

По умолчанию просто удаляет запись (`uninstall=false`).
`uninstall=true` перед удалением записи снимает расширение RSVData с базы —
зеркало установки, но точка `/remove` первая: расширение 1.3.6+ удаляет
само себя (динамически, монопольный режим не нужен) → при неудаче EDT через
MCP:RSV (`uninstallExtension`; нужна EDT-связь цели и открытый проект; на
опубликованной базе может не пройти — сеансы держат базу, держатели придут
поимённо) → конфигуратор (`/DeleteCfg -Extension RSVData`, точная сборка
платформы базы; ключ авторизации так же НЕ обязателен — базы без
пользователей обслуживаются запуском без `/N /P`). Тот же ключ `platform`
служит фолбэком версии (если записи цели он не достался и авто-резолв
молчит).

Та же предпроверка перед запуском: заранее мёртвая цепочка (точка /remove
недоступна, нет источника строки подключения или версии платформы) даёт
отказ сразу, без задания. Бинарник `--rsvdatabinary` удалению не нужен.

Удаление тоже идёт ФОНОВЫМ ЗАДАНИЕМ: id в ответе, статус и отчёт —
`job_status(job_id="ид")`. По завершении задания: «Отключено» (базу держат
активные сеансы, удалить сейчас нельзя) — не ошибка: расширение переведено
в неактивное и не загружается, доудалить можно позже. Расширения нет /
удалено / отключено — запись цели удаляется автоматически; удалить не
удалось ни одним способом — запись СОХРАНЯЕТСЯ (доступ к базе из роутера и
креды для повторной попытки), отчёт назовёт причину и следующий шаг. Сразу
после «удалено» пул HTTP-сеансов ~25–30 с дорабатывает старым кодом: запросы
к базе отвечают 500 «Расширение RSVData не найдено», затем 404 — это норма,
а не ошибка удаления. Креды для варианта конфигуратора читаются из
targets.json до разрушающего шага — при неудачном удалении они не теряются.

## list_targets

`list_targets(check=true)` пингует каждую цель и для RSVData 1.3.5+
показывает версию и хеш расширения; `check=false` — без сетевых запросов.

## update_targets

Массовое самообновление RSVData на уже зарегистрированных целях: POST
`<база>/hs/rsvdata/update` телом бинарника `--rsvdatabinary`.
Параметр `targets` — алиас, массив или строка с запятыми; без параметра — все.
Тот же шаг `/update`, что в цепочке установки, но без регистрации и без
вариантов EDT/конфигуратора (они — только для первичной установки на базах
без точки /update): цель без `/update` попадает в отчёт с подсказкой про
`register_target(install=true)`. Отчёт построчный + итог; новый код
подхватывают новые HTTP-сеансы (пул живёт до ~25 с — сразу после обновления
ping может ещё показывать старую версию).

Без бинарника — отказ сразу (см. таблицу в начале файла).

## job_status

`job_status(job_id)` — статус фонового задания: «выполняется» (пройденные
шаги + время) или полный отчёт цепочки; без параметра — список последних
заданий. Задания живут в памяти процесса роутера: перезапуск их теряет
(цепочки безопасно повторяются); список инструментов клиента может
кэшироваться — новый инструмент появится после пересоздания MCP-сессии.

## get_rsvdata

Бинарник расширения RSVData (.cfe): путь, HTTP-ссылка `/bin/rsvdata.cfe`,
рецепт внедрения через rsv — importProject → sync_database → публикация на
веб-сервере. Путь задаётся только при старте, `--rsvdatabinary`; раздаётся и
по HTTP для удалённых клиентов `--network`. Без бинарника отвечает
инструкцией (см. таблицу в начале файла).

## help_router

Справка самого роутера: маршрутизация, цели, auth, бинарник. Справка
инструментов данных — апстримная: `help` без параметров — обзор самой базы,
`help topic=<имя>` — раздел справки RSVData.

## Ошибки апстрима

Ошибки апстрима классифицируются одним блоком для всех вызовов: 401 —
инструкция по настройке авторизации; 404 — «публикация не найдена»; 409 —
несовпадение версий ПЛАТФОРМЫ (модуль расширения веб-сервера vs сервер 1С;
текст ответа сервера приводится целиком); 5xx — внутренняя ошибка
веб-сервера (часто сервер 1С остановлен); сеть — цель недоступна. Каждый
блок заканчивается требованием к ИИ-агенту: ошибку не диагностировать
самостоятельно (без ping/curl напрямую к базе) и показать сообщение
пользователю как есть.
